Theatour

An augmented-reality educational game that guides new students through campus via story and location-based puzzles.

Theatour is an AR educational game demo developed over 4 months by a team of 8 students. Inspired by Niantic's Ingress and the designer's own college onboarding experience, the project uses augmented reality, location services, and procedurally generated storytelling to create an immersive campus tour for new students.

Procedural Narrative

Problem

Writers and designers needed a way to contribute story content without being blocked by technical implementation. Many team members had never made a digital game before, and there was no clear pipeline for non-programmers to author narrative content. Every story addition required engineering support.

Outcome

A developer-friendly procedural narrative system that allowed writers and designers to author story snippets which the engine would dynamically assemble based on player progress and location. Non-technical team members could contribute story independently, and the system remained flexible enough for rapid iteration and content changes.

Process

Building a system that enabled contribution across skill levels required careful architecture:

  1. Separation of concerns: Designed the system to cleanly separate gameplay logic from narrative content. This allowed programmers to build systems while writers and designers worked independently.
  2. Modular content snippets: Instead of monolithic story sequences, broke narrative into developer-written snippets that could be mixed and matched procedurally.

  3. Contextual assembly: Story was procedurally generated at runtime based on two variables: player progress (how far through the game) and location (where the player is on campus).
  4. No-code authoring: Writers and designers filled in content tables without touching code, allowing for meaningful contributions without technical blockers.

Solution

A modular procedural narrative system with a clean data structure as the interface between technical and creative teams. Story snippets authored by writers and designers are assembled at runtime based on player progress and location, generating unique narrative paths for players to experience.

Impact

  • Enabled non-programmers to contribute narrative content independently
  • Allowed rapid story iteration and testing without technical bottlenecks
  • Supported multiple narrative paths based on player progress and location
  • Created a scalable system where new content could be added by following established data patterns

Learnings

When you separate concerns properly and create clear interfaces, team members with different skill sets can work independently and in parallel. The best technical systems are the ones that disappear from the perspective of non-technical collaborators.

Cost Optimization: Google Maps API

Problem

The game relied on constant Google Maps API calls to maintain location services and map data, creating redundant network traffic and expensive service costs. The API was being queried continuously throughout gameplay, far more often than necessary given the actual usage patterns and constraints.

Outcome

Disconnected the game from the Google Maps API while retaining full location services and map functionality. Reduced API calls from constant redundant queries to a single check per app session, dramatically cutting service costs while maintaining the same user experience.

Process

The optimization came from understanding actual usage constraints:

  1. Identified the constraint: Recognized a critical constraint: players would only ever use this app while physically at the university. The game was designed for a specific location, not general use.
  2. Designed the boundary check: Instead of continuous API polling, implemented a single latitude/longitude check when the app opens to verify the player is within the school's geographic bounds.
  3. Pre-installed map data: On API connection, the local University map was downloaded and saved to the device.
  4. Retained full functionality: Location services and map data remained available throughout gameplay, and redundant API calls were eliminated.
  5. Cost-benefit analysis: Instead of potentially hundreds of API calls per session, which was unfeasible for an independent demo, the app now makes exactly one per session.

Solution

Replace continuous Google Maps API polling with a single boundary check on app open. When the app launches, verify via latitude/longitude that the player is within the school's geographic bounds. If they are, proceed with the game using cached map data and local location services. If not, prevent access or display an out-of-bounds message. This eliminates redundant API calls while maintaining the same functionality and user experience.

Impact

  • Dramatically reduced projected service costs
  • Maintained full location services and map functionality
  • Improved app performance by reducing network overhead
  • Enabled the project to stay within budget constraints while using expensive geolocation APIs

Learnings

Understanding the actual context and constraints of how your product will be used reveals optimization opportunities that generic solutions miss. We didn't need to eliminate the Maps API entirely, we just needed to understand that it would only be used once per session. Also, cost-benefit analysis of third-party tools and services should happen early in development to prevent expensive surprises.
